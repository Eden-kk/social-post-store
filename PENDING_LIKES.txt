Durable pending likes (local prototype)
======================================
Purpose: accept a LIKE intent on a partitioned node without falsely declaring a
Raft commit. Local durable admission is not proof of cross-region durability.
The fixed three JVMs simulate nodes; no physical-region or high-QPS claim.

HTTP API (loopback demo, no authentication)
------------------------------------------
GET /social/likes/queue -> origin=<UUID>
POST /social/likes/pending
  X-Pending-Origin: original queue UUID
  X-Request-ID: unique action ID, reuse unchanged for retries
  body: LIKE<TAB>post<TAB>user<TAB>writer<TAB>positive_sequence<TAB>true|false
Response: PENDING, or the retained terminal result on an identical retry.
POST /social/likes/result
  X-Pending-Origin: original queue UUID
  body: request ID
Response: PENDING | NOT_FOUND | COMMITTED\n<exact OK result> |
          REJECTED\n<exact ERR result>.
HTTP 200 carries these application statuses; wrong origin/payload is 400,
storage failure or retained-capacity exhaustion is 503, not accepted PENDING.
Retry/status must return to this same node incarnation; no transparent failover.

Persistence and delivery
------------------------
PendingLikes owns queue.bin (checkpoint), queue.wal (write-ahead log), and an
exclusive queue.lock. Each admission or terminal outcome appends its sequence,
incarnation, payload-bound ID, command and exact outcome to queue.wal; the file
and directory are forced BEFORE publishing the in-memory transition or response.
The record has a bounded length plus its complement and a SHA-256 payload digest.
I/O errors fail closed; a failed force may have an uncertain durable outcome,
so retry the same ID after restart, never invent a replacement ID.

Every 128 transitions (or explicit checkpoint()), all retained state and the
covered sequence are checksummed, forced to queue.tmp, atomically renamed to
queue.bin and directory-forced. Only THEN is queue.wal truncated and forced.
Recovery skips checked records already covered by the checkpoint and applies
later records in contiguous sequence. Old v1 queue.bin files remain readable;
they gain a WAL before their first v2 checkpoint without losing the incarnation.
Checkpoint does not expire terminal outcomes or release retained-entry capacity.
Each append is still synchronously forced, and checkpoint still writes full state;
no throughput or latency improvement is claimed without a benchmark.

Under an interrupted-append crash model, an incomplete final header/payload is
truncated to the last valid record before appending again. A complete corrupt
header/payload, sequence gap, wrong incarnation or invalid transition fails closed.
This cannot distinguish external truncation of an acknowledged file from a torn
append; it is not protection against arbitrary disk loss or malicious modification.

A single worker visits retained pending records every 300ms after a completed
round. It submits the SAME social:<ID> and command through the local Raft node.
Followers can forward to fixed peers through /raft/like, with both sender and
receiver partition gates; forwarding endpoints only submit locally, not recurse.
Each remote forwarding attempt has a 1100ms total response deadline including
the body, a 2048-byte body cap, and cancellation on timeout or worker interruption.
This bounds a stalled peer's effect on the next pending intent, not total queue latency.
Raft majority/current-term rules remain unchanged. NOT_LEADER, UNKNOWN,
transport failures retain PENDING. OK/ERR results become durable terminal state.
Transient peer errors do not falsely reject an intent. A missing/deleted post,
writer mismatch, equal-sequence payload conflict or ID conflict CAN reject it.

Crash windows
-------------
Before journal durable: no PENDING acknowledgement. After journal durable but
before submit: restart retries. After Raft commit but before journal result save:
restart resubmits the same ID; Raft's committed payload/result dedup avoids a
second effect. After terminal save but lost HTTP reply: retry returns retained
result. A persisted intent does not imply its desired state eventually wins:
OK STALE and OK SAME are terminal acknowledgements, with their exact result
exposed; a fresh GET_LIKE is necessary to query current authoritative state.

Ordering and capacity
---------------------
event ID identifies retries; writer + positive sequence identifies logical order;
desired boolean distinguishes like/cancel. Existing SocialState atomically applies
the relationship and count delta. Sequence 1=true,3=true,2=false ends true/count1.
This is not multi-device arbitration. One writer binds the relationship.
Queue retains terminal entries indefinitely for payload binding (no eviction,
expiry or cancel). At 10000 total entries NEW intents reject; existing retry and
status still work. This bounds storage, not sustained throughput. Clients must
not silently create a fresh ID after an ambiguous result. No UI or status push.

Boundaries
----------
Local disk loss can lose PENDING and its status. Raft commit durability is only
that of the configured quorum, not a deployment-independent regional guarantee.
No MQ is required here: the durable intent journal plus worker is sufficient for
the minimal implementation. Existing view MQ is unrelated. No production auth,
dynamic membership, terminal-result eviction, backup, multi-region placement or SLA.

Verification
------------
sh build.sh
java -cp build/classes lab.PendingLikesTest
java -cp build/classes lab.PendingWalTest
java -cp build/classes lab.PendingSlowPeerTest
java -cp build/classes lab.PendingLikesClusterTest
Unit tests: restart, payload/origin conflict, bounded admission, invalid oversized
input, exclusive lock, terminal error/stale result, unknown retry, checksum failure,
admission-persist failure, commit-before-result-persist failure, shutdown interrupt.
Real three-process test: follower ingress, partition-safe pending, process restart,
healing without requiring ingress election, duplicate exact count, 1/3/2 ordering,
missing/deleted-post rejection, terminal restart, real Raft commit followed by forced queue
result-save failure and replay. WAL-write failure injection temporarily replaces
queue.wal with a directory while preserving its prior durable bytes for restart.
Checkpoint tests model installed checkpoint + old WAL, failed pre-rename checkpoint,
torn final header/payload repair, append-after-recovery, checksum/header corruption,
automatic checkpoint and v1 migration. These are deterministic file-state fault
models, not hardware power-loss/fsync fault injection.
Slow-peer test sends headers then stalls the body, verifies later intent progress,
interruptible close, and exact 2048-byte/oversized 2049-byte response boundaries.
